# Backend Internal Standards

- **Layering**: `handler.go` (HTTP only) → `service.go` (business logic, depends on a narrow repository interface) → `repository.go` (wraps sqlc `Queries`). See `internal/accounts` or `internal/articles` — they are deliberately kept structurally parallel, since a template propagates by copy-paste.
- **Request decoding**: handlers never call `json.NewDecoder` directly. Use `request.DecodeAndValidate` (`internal/httpserver/request`), which applies the shared 1 MiB `http.MaxBytesReader` cap, decodes, and runs `validator` struct-tag validation, writing the standard 422 (or 413) envelope on failure. There is exactly one `validator.Validate` instance (`request.Validate`) for the whole process.
- **Repository errors**: the `ErrNotFound` sentinel and the pgx/Postgres error translation live once in `internal/db/dberr` (`WrapNotFound`, `IsUniqueViolation`, `IsForeignKeyViolation`); each app re-exports `ErrNotFound` for its callers. Enforce uniqueness with a DB constraint and map SQLSTATE `23505` in the repository (see `accounts.Repository.CreateUser`) — a SELECT-then-INSERT pre-check in the service is a TOCTOU race that surfaces as a 500 under concurrency.
- **Pagination**: compute SQL `OFFSET` in `int64` and cap it (`articles.maxOffset`); `(page-1)*pageSize` in `int32` overflows to a negative offset on large page numbers and 500s. Use keyset pagination if you genuinely need deep pages.
- **DB/migrations**: all schema changes go through goose migrations in `internal/db/migrations/`; all queries are hand-written SQL in `internal/db/queries/`, compiled by sqlc into `internal/db/sqlc/` — no ORM, no query builder.
- **Secrets/config**: all config flows through `internal/config.Config` (or its narrower `ServerConfig`/`DatabaseConfig` siblings for tools that only need part of it); never call `os.Getenv` outside that package.
- **Shared JWT primitives**: token creation/parsing lives in `internal/jwtutil` (extracted out of `internal/accounts` to avoid an import cycle with `internal/realtime`, which also needs to verify access tokens).
- **Observability**: structured logging via `log/slog` (JSON in prod, via `internal/logging`); `X-Request-ID` is generated/propagated by `internal/httpserver/middleware.RequestID`. No distributed tracing in this version.
- **Testing**: unit tests use hand-written fakes implementing narrow repository interfaces (no mocking framework); integration tests use `testcontainers-go` and are gated behind `-tags=integration` so `go test ./...` never needs Docker.
- **Periodic tasks**: scheduled by `cmd/scheduler` (`asynq.Scheduler`, the Celery Beat equivalent) as a separate process from `cmd/worker` — one scheduler, N workers. Register new periodic tasks there; put the handler with its app (`internal/<app>/tasks.go`), or in `internal/tasks` if it is pure infrastructure like the heartbeat.
- **Linting**: `.golangci.yml` is checked in and CI runs a pinned golangci-lint against it. `gosec` is enabled deliberately — it is what catches missing server timeouts (G114) and unchecked integer narrowing (G115).
- **Task idempotency**: asynq task handlers (`internal/articles/tasks.go`) must be safe to run twice — this template's example re-derives everything from the task payload's ID rather than trusting local state.
- **Dual writes (commit + enqueue)**: `articles.Service.Publish` commits the status change and *then* enqueues the webhook task. These are two systems and cannot be made atomic this way. If the enqueue fails, the template logs at `Error` with the article ID and **still returns success** — the publish really did happen, and returning 500 would invite a retry that sees `transitioned == false` and silently succeeds without ever sending the webhook.

  This is a known, accepted gap in the example, not a pattern to copy blindly. The real solution is the **transactional outbox**: in the same transaction as the state change, `INSERT` a row into an `outbox` table describing the task; a separate relay (a polling asynq task, or Postgres logical decoding/CDC) reads unsent outbox rows, enqueues them, and marks them sent. Because the state change and the outbox row commit or roll back together, the task can never be lost — only delivered late, and possibly more than once, which is why task handlers must be idempotent anyway. Adopt it before you depend on these events for anything that matters (billing, notifications, downstream sync).
